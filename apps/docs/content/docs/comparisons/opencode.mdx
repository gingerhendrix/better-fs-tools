OpenCode is an open-source terminal coding agent published by anomalyco. Its model-facing file family is seven dedicated tools: `read`, `glob`, `grep`, `write`, `edit`, `apply_patch`, and `bash`. The mutation set changes with the model: `apply_patch` replaces `write` and `edit` for GPT model IDs. The read tool wraps its output in `path`, `type`, and `content` tags, lists directories itself, and appends project instruction files to the result as a system reminder.

## Tool inventory

| Tool | Purpose | Default | Notes |
|---|---|---|---|
| `read` | Read a text file, image, PDF, or directory page | Yes | Present unless the `read` permission is wholly denied |
| `glob` | Find file paths by glob pattern | Yes | Bundled ripgrep file enumeration |
| `grep` | Search file contents by regex | Yes | Bundled ripgrep JSON matches |
| `write` | Create or replace a whole file | Model dependent | Hidden for model IDs containing `gpt-`, except `oss` and `gpt-4` |

There is no separate list tool: `read` on a directory lists it. There is no persistent shell, PTY, or process-handle tool. Plugins can change any description or parameter schema through the `tool.definition` hook, and provider transforms can rewrite the JSON Schema before the model sees it. The contracts below are the pre-transform ones.

## Read

### Signature

```ts
read({ filePath: string, offset?: number, limit?: number })
```

`filePath` is described as absolute. Relative paths are accepted and resolve against the instance directory. `offset` is one-based; a missing or zero offset becomes `1`. `limit` defaults to 2000 lines. The schema types both as non-negative integers.

### Description

`read`: 1158 characters, 1158 bytes, 15 lines, approximately 259 tokens.

The string states the absolute-path rule, the 2000-line default, the one-indexed `offset`, the line prefix shape with a worked example, directory listing with a trailing `/` on subdirectories, the 2000-character line cut, image and PDF attachments, and three habits: use `grep` and `glob` first, call `read` in parallel, and avoid small repeated slices.

**`read` (1158 characters)**

```text
Read a file or directory from the local filesystem. If the path does not exist, an error is returned.

Usage:
- The filePath parameter should be an absolute path.
- By default, this tool returns up to 2000 lines from the start of the file.
```

### Path handling

Relative paths resolve against the instance directory. On Windows the path passes through `FSUtil.normalizePath`, which resolves to a real path when one exists. There is no tilde expansion and no URL handling. A path outside the instance directory or Git worktree triggers an `external_directory` permission ask on its parent directory glob before any read.

When `stat` reports not found, the tool lists the parent directory and keeps entries whose lower-cased name contains the requested basename or is contained by it. The first three become suggestions. The candidate list is never used to resolve the read.

```text
File not found: <path>

Did you mean one of these?
<dir>/<candidate>
```

Without candidates the message is `File not found: <path>`.

Symlinks: the containment check is lexical and runs before any canonicalisation, so an in-worktree symlink whose target sits outside the project passes without the external-directory prompt. For directory listings, each entry's symlink target is stat-ed only to decide whether to append `/`.

### Notable

- After the closing `content` tag, a `system-reminder` block can follow with the content of instruction files that apply to the path. These files are resolved from the session and the target path, so the result can carry text that is not in the requested file.
- A successful text read starts an LSP warm-up in the background.
- Directory reads use `readdir`, stat every entry with unbounded concurrency, sort by locale, then apply `offset` and `limit`. Entries have no line numbers.
- The byte cap stops the stream with a tagged `ReadStop` error. The tool-call abort signal is not used.
- No repeat-read guard, no redaction, no explicit empty-file notice.
- The description tells the model it can read images and PDFs. Other media attachments are not produced; a non-text file outside the four image formats and PDF is refused as binary.

## Edit

### Signature

```ts
write({ filePath: string, content: string })
edit({ filePath: string, oldString: string, newString: string, replaceAll?: boolean })
apply_patch({ patchText: string })
```

`replaceAll` is a boolean. `patchText` is raw text in the OpenCode patch envelope: `*** Begin Patch`, file sections headed `*** Add File:`, `*** Update File:` with optional `*** Move to:`, or `*** Delete File:`, then `*** End Patch`. The registry shows `apply_patch` in place of `write` and `edit` for model IDs containing `gpt-`, except those containing `oss` or `gpt-4`. All three ask under the shared `edit` permission, and `Permission.disabled` maps all three to that key.

### Description

`write`: 623 characters, 623 bytes, 9 lines, approximately 124 tokens.
`edit`: 1369 characters, 1369 bytes, 11 lines, approximately 289 tokens.
`apply_patch`: 1092 characters, 1098 bytes, 34 lines, approximately 263 tokens.

`write` tells the model an existing file must be read first and that the tool fails otherwise; the runtime has no such check. `edit` names the line prefix format as number, colon, space, tells the model to keep indentation after that prefix, and quotes two failure messages. The strings the runtime throws differ from those quoted: see Errors. `apply_patch` explains the envelope grammar with an example and two rules: every section needs a header, and new lines carry a `+` prefix.

### Whole-file write

`write` reads the current content to build a permission preview diff, asks once, then writes with `FSUtil.writeWithDirs`. That helper retries a missing-parent failure after creating the parent directory recursively. The write is a direct platform write; there is no temporary file and rename. An existing UTF-8 BOM is preserved. Line endings: `edit` preserves CRLF; for `write` the content is written as supplied. Mode preservation: Not surveyed.

After the write, configured formatters run in the instance directory with the path substituted for `$FILE`. A formatter failure is logged and the write stands. The tool then touches the LSP document, collects diagnostics, and publishes file and watcher events.

### Matching

`edit` runs a cascade of nine replacers in order: exact, line-trimmed, block-anchor, whitespace-normalised, indentation-flexible, escape-normalised, trimmed-boundary, context-aware, and multi-occurrence. The first candidate found in the file wins. The model is not told which stage matched. Without `replaceAll`, a candidate that occurs more than once is skipped and the next stage runs; when every stage is exhausted the tool reports multiple matches. A guard refuses a fuzzy match whose span is much larger than `oldString`. An empty `oldString` creates a new file and errors when the path already exists. Equal `oldString` and `newString` is an error.

### Multi-file patch

Present as `apply_patch`. The tool parses every hunk first and derives all changes in memory. It verifies that each Update and Delete target reads and matches before it asks for one shared `edit` approval. After approval it applies file by file in order: a move writes the destination then removes the source; a delete calls `remove`. Formatting and event publication run per file. There is no staging area, transaction, or rollback, so a later I/O failure leaves the earlier files changed. An Add on an existing path overwrites it; a source test covers this. A verification failure on a later file happens before any write, and a source test confirms that a preceding Add is not on disk at that point.

### Verification and mutation state

| Concern | Behaviour |
|---|---|
| Read-before-write | Described to the model for `write` and `edit`; not enforced |
| Stale-file check | None. No mtime, hash, or read ledger |
| Lock | `edit` holds an in-process semaphore keyed by `realpath` (or the normalised path for a new file) from the read through the approval wait to the write. `write`, `apply_patch`, `bash`, and other processes take no lock |
| Cross-process coordination | None |
| Post-write checks | LSP diagnostics for the file are appended to the model text. Formatters can change more than the requested span; `edit` and `apply_patch` re-read after formatting for the final diff |
| Change tracking | Mutation tools publish file and watcher events; the session takes Git-backed snapshots around steps |

### Output

| Tool | Model text |
|---|---|
| `write` | `Wrote file successfully.` then, when present, `LSP errors detected in this file, please fix:` with a diagnostics block, and `LSP errors detected in other files:` for at most five other files |
| `edit` | `Edit applied successfully.` then the same file-level diagnostics block when present. The unified diff and addition and deletion counts go to metadata, not to the model |
| `apply_patch` | `Success. Updated the following files:` followed by one summary line per file |

### Notable

- The permission request for all three tools carries a preview diff.
- No notebook editor, no undo tool, no checkpoint tool in this family.
- The `edit` description promises exact matching; the runtime accepts the fuzzy cascade above. The description's quoted failure strings (`oldString not found in content`, `Found multiple matches for oldString. Provide more surrounding lines ...`) are not the strings the runtime throws.

## Shell

### Signature

```ts
bash({ command: string, timeout?: number, workdir?: string })
```

`timeout` is a positive integer in milliseconds; the default is 120000 unless a runtime flag overrides it. A negative value is rejected. `workdir` sets the working directory. The tool ID and permission key are `bash` on every supported shell.

### Description

`bash`: 4628 characters, 4628 bytes, 61 lines, approximately 1056 tokens. Rendered for `os=linux`, `shell=bash`, the default 2000-line and 51200-byte output limits, the 120000 ms timeout, and `/tmp/opencode` as the temporary directory. PowerShell and `cmd.exe` profiles render different, longer text.

The string tells the model to use `workdir` instead of `cd`, that `/tmp/opencode` is pre-approved, to leave file operations to the dedicated tools, to verify parent directories and quote paths, how the timeout and truncation work, to run independent commands as parallel calls and dependent ones with `&&`, and a set of git rules. It opens by calling the session persistent; each call runs one child process.

### Working directory and environment

The working directory is the instance directory unless `workdir` is given. The environment starts as the full `process.env`; the plugin `shell.env` hook can add or replace variables. OpenCode selects an acceptable configured shell and adapts the prompt and invocation for POSIX shells, PowerShell 7, Windows PowerShell 5.1, and `cmd.exe`. PowerShell launches with `-NoLogo -NoProfile -NonInteractive -Command`; other shells receive the command through the selected shell. Login shell: Not surveyed.

### Process lifecycle

| Aspect | Behaviour |
|---|---|
| Model | One child process per call. No session, resume token, or persistent cwd |
| Background | None. No process handle is returned |
| stdin | Ignored after launch |
| Detach | POSIX children are detached; Windows children are not |
| Cancellation | The child exit, the tool abort signal, and the timeout race. Abort or timeout calls `kill` with a three-second force-kill deadline |
| Grandchildren | Cleanup of deliberately backgrounded grandchildren after the shell exits: Unverified. The source does not establish it |

### Output limits

| Aspect | Behaviour |
|---|---|
| Collection | stdout and stderr are one combined stream. The full stream is kept in memory as a rolling tail and spilled to a truncation file once it passes the byte threshold |
| Model-visible budget | 2000 lines and 50 KiB by default; `tool_output.max_lines` and `tool_output.max_bytes` override. The preview is the tail |
| Truncation text | `...output truncated...` then `Full output saved to: <file>` then the tail |
| Spill file | Under the truncation directory; files named `tool_*` are removed after seven days by an hourly task |
| Empty output | `(no output)` |
| UI progress | Call metadata is updated during execution with the last 30000 characters |

`bash` always sets `metadata.truncated`, which makes the generic tool-output wrapper skip its own second pass. The generic wrapper, used by other tools, returns a head preview plus a hint naming `Grep` and `Read` with `offset` and `limit`.

### Sandbox

None. No OS sandbox, seccomp profile, container, macOS Seatbelt policy, or restricted credential is in this path. The network is unrestricted. The child inherits the OpenCode process account. The repository uses the word "sandbox" for project worktrees, which is a naming choice separate from process isolation.

### Approval

Before execution the command is parsed with Tree-sitter Bash or PowerShell. Each parsed command except a directory change becomes a `bash` permission pattern. The "always" suggestion comes from a command-prefix arity table, giving patterns such as `git checkout *`, `npm run dev *`, or `rm *`. A second static pass recognises filesystem commands (`rm`, `cp`, `mv`, `mkdir`, `cat`, the PowerShell content and item commands, and `cmd.exe` file commands), resolves literal paths, selected environment variables, home paths, and wildcard prefixes, and raises an `external_directory` request for paths outside the project before the `bash` request.

The parser is an approval aid. Command substitution, most variables, and expressions are skipped during path collection, and commands outside the static set contribute no paths. With the default `build` agent every `bash` pattern is allowed, so no prompt appears unless the user changes rules. Rejecting one pending request rejects every pending request in the session. A command the parser cannot read fails with `Failed to parse command`.

### Notable

- A non-zero exit code is a successful tool result. The code is in `metadata.exit`, not in the model text.
- Timeout and abort also return normal results with `exit: null` and a `shell_metadata` block appended to the text:

```text
<shell_metadata>
shell tool terminated command after exceeding timeout <n> ms. If this command is expected to take longer and is not waiting for interactive input, retry with a larger timeout value in milliseconds.
</shell_metadata>
```

- The abort marker is `User aborted the command` in the same block.
- No PTY, no streaming to the model, no interactive input.

`glob` asks for the `glob` permission with the pattern, resolves `path` against the instance directory, rejects a path that is a file with `glob path must be a directory: <path>`, asks for external-directory access when needed, and returns absolute paths one per line, or `No files found`. Truncation is detected when exactly 100 entries return.

`grep` accepts a file or directory target, resolves an existing target to its real path, uses the containing directory as ripgrep's cwd for a file, and groups results under absolute paths: `Found <n> matches`, then `<path>:` lines, then `  Line <n>: <text>` rows. Zero matches return `No files found`. An empty pattern fails with `pattern is required`. Neither tool passes the tool-call abort signal to ripgrep.

### Description

`glob`: 517 characters, 517 bytes, 7 lines, approximately 109 tokens.
`grep`: 657 characters, 657 bytes, 9 lines, approximately 149 tokens.

Both strings are bullet lists. `glob` names the pattern syntax, says to use it for filename search, points open-ended searches at a Task tool, and asks for speculative parallel searches. `grep` names the regex syntax and the `include` filter, describes the output as paths with line numbers, and tells the model to use `rg` through the shell for counting matches.

**`glob` (517 characters)**

```text
- Fast file pattern matching tool that works with any codebase size
- Supports glob patterns like "**/*.js" or "src/**/*.ts"
- Returns matching file paths
- Use this tool when you need to find files by name patterns
- When you are doing an open-ended search that may require multiple rounds of globbing and grepping, use the Task tool instead
- You have the capability to call multiple tools in a single response. It is always better to speculatively perform multiple searches as a batch that are potentially useful.
```

**`grep` (657 characters)**

```text
- Fast content search tool that works with any codebase size
- Searches file contents using regular expressions
- Supports full regex syntax (eg. "log.*Error", "function\s+\w+", etc.)
- Filter files by pattern with the include parameter (eg. "*.js", "*.{ts,tsx}")
- Returns file paths and line numbers with matching lines
- Use this tool when you need to find files containing specific patterns
- If you need to identify/count the number of matches within files, use the Bash tool with `rg` (ripgrep) directly. Do NOT use `grep`.
- When you are doing an open-ended search that may require multiple rounds of globbing and grepping, use the Task tool instead
```

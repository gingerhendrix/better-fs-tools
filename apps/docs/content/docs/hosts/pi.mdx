`@better-fs-tools/pi` gives the [Pi coding agent](https://www.npmjs.com/package/@earendil-works/pi-coding-agent) the Better FS Tools `read`, `edit`, and `write`. They replace Pi's built-in tools of the same names. The package can also add `apply_patch`, and a `bash` tool in Pi's own shape. Each call can only touch files under the working directory of that call.

## Install

To use the tools in Pi as they are, install the package with Pi's own command:

```sh
pi install npm:@better-fs-tools/pi
```

Pi writes the package to your user settings. Add `-l` to write it to the project settings in `.pi/settings.json`. To try the tools for one run only, start Pi with `pi -e npm:@better-fs-tools/pi`.

To write your own extension with `createPiFsTools()`, install the package and its peers in your extension's project:

```sh
npm install @better-fs-tools/pi @better-fs-tools/read @better-fs-tools/write @earendil-works/pi-coding-agent typebox
```

`@earendil-works/pi-coding-agent` (`^1.0.0`) and `typebox` (`^1.3.16`) are required peers. Pi versions before 1.0 are not supported. The package needs Node 24 or later.

## What the package registers

The package has a `pi.extensions` entry. When Pi loads the package, the entry calls `createPiFsTools()` with no options and registers three tools:

| Tool          | Registered | Notes                                                              |
| ------------- | ---------- | ------------------------------------------------------------------ |
| `read`        | Yes        | Returns images, as Pi's own `read` does                            |
| `edit`        | Yes        | Pi's input shape, and Pi draws the diff                            |
| `write`       | Yes        | Pi's input shape                                                   |
| `apply_patch` | No         | Register it from your own extension                                |
| `bash`        | No         | Pi's own `bash` stays. Register `createPiBashTool()` to replace it |

The entry has no read store, so `edit` and `write` do not check for a read first. Writes stay inside `ctx.cwd`. The entry writes no settings file and no session file.

The same entry is also available as the default export of `@better-fs-tools/pi/extension`.

## Write your own extension

To set options, add `apply_patch`, or turn on [read before write](/guides/write/read-before-write), register the tools from your own extension with `createPiFsTools()`:

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { createPiFsTools } from "@better-fs-tools/pi";
import { denyPaths, memoryStore, unicodeRepair } from "@better-fs-tools/read";
import { hashlineFormat } from "@better-fs-tools/read/formats";
import { protectPaths } from "@better-fs-tools/write";

export default function fsToolsExtension(pi: ExtensionAPI): void {
  // Four tools with one read store, so edit and write need a read first. The
  // store and apply_patch are opt-in.
  const tools = createPiFsTools({
    state: memoryStore(),
    read: {
      resolve: unicodeRepair({ note: false }),
      authorize: denyPaths(["**/.env", "**/.env.*"]),
      formatter: hashlineFormat(),
    },
    edit: { authorize: protectPaths() },
    write: { authorize: protectPaths() },
    applyPatch: { authorize: protectPaths() },
  });
  pi.registerTool(tools.read);
  pi.registerTool(tools.edit);
  pi.registerTool(tools.write);
  pi.registerTool(tools.applyPatch);
}
```

The tools share one digest, one lock manager, one clock, and one cache of filesystems. With `state`, they also share one read store. Set the shared options once, at the top level:

| Option                  | Default                           | Meaning                                                                                 |
| ----------------------- | --------------------------------- | --------------------------------------------------------------------------------------- |
| `state`                 | `null`                            | The read store. `null` turns read before write off. `memoryStore()` turns it on         |
| `digest`                | `nodeDigest()`                    | The digest for read records                                                             |
| `locks`                 | `piMutationQueueLocks()`          | The lock manager of the write tools. See [Locks](#locks)                                |
| `clock`                 | `() => new Date()`                | The clock of the tools and the store                                                    |
| `applyPatch`            | off                               | `true`, or an options object, adds `apply_patch`                                        |
| Root options            | see [Root options](#root-options) | `denyRoots`, `symlinks`, `hardLinks`, `newFileMode`, `newDirectoryMode`                 |
| `read`, `edit`, `write` | `{}`                              | The options of one tool. See the [read](/guides/read) and [write](/guides/write) guides |

The result has `read`, `edit`, `write`, and `applyPatch` (`null` when it is off). It also has the shared `state`, `digest`, `locks`, and `clock`, and `invalidate(path, call?)`. See [Forget a read after a bash command](#forget-a-read-after-a-bash-command).

The bundle takes `state` as one store or `null`. It does not take a store factory of the call. These options throw `TypeError`:

- An unknown key at the top level, for example `bash`.
- A shared option inside one tool's options: `state`, `digest`, `locks`, `clock`, or a root option.
- `fs`, `cwd`, or `allowedRoots`, at any level. See [Each call uses ctx.cwd](#each-call-uses-ctxcwd).

```text
TypeError: Unknown createPiFsTools option: bash
TypeError: createPiFsTools read options cannot set state: set it once at the top level
```

## Register one tool

Each tool also has its own factory: `createPiReadTool()`, `createPiEditTool()`, `createPiWriteTool()`, and `createPiApplyPatchTool()`. This extension registers only the read tool, with the path parameter renamed to `file_path`:

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { createPiReadTool } from "@better-fs-tools/pi";
import { denyPaths, unicodeRepair } from "@better-fs-tools/read";
import { hashlineFormat } from "@better-fs-tools/read/formats";
import { defaultReadSignature } from "@better-fs-tools/read/signature";

export default function readExtension(pi: ExtensionAPI): void {
  pi.registerTool(
    createPiReadTool({
      signature: defaultReadSignature({ name: "read", names: { path: "file_path" } }),
      resolve: unicodeRepair({ note: false }),
      authorize: denyPaths(["**/.env", "**/.env.*"]),
      formatter: hashlineFormat(),
    }),
  );
}
```

`createPiReadTool()` takes every `createReadTool()` option except `fs`. It also takes `signature`, `promptSnippet`, `promptGuidelines`, `denyRoots`, and `symlinks`. The write factories take every option of `createEditTool()`, `createWriteTool()`, or `createApplyPatchTool()` except `fs`, plus the same Pi options and all five root options. Each single factory defaults `digest` to `nodeDigest()`.

A single factory shares no read store with another one. No tool has a read store unless you pass one. The write factories default to `piMutationQueueLocks()`, which uses Pi's own queue, so they already wait for each other. To use single factories with read before write, pass one store to all of them:

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { createPiEditTool, createPiReadTool, createPiWriteTool } from "@better-fs-tools/pi";
import { memoryStore } from "@better-fs-tools/read";

export default function singleToolsExtension(pi: ExtensionAPI): void {
  // One read store for the three tools. The write tools share Pi's file queue
  // by default.
  const state = memoryStore();
  pi.registerTool(createPiReadTool({ state }));
  pi.registerTool(createPiEditTool({ state }));
  pi.registerTool(createPiWriteTool({ state }));
}
```

`createPiFsTools()` does the same with less code. Use a single factory when you register one tool only.

## Use Pi from code (SDK)

`@earendil-works/pi-coding-agent` is also an SDK. `createAgentSession()` runs the same session as the `pi` command, in your own Node or Bun process. The tools from `createPiFsTools()` work there with no change.

### Replace the built-in tools

Give the tools to `customTools`. A custom tool with the name of a built-in tool replaces that built-in tool, so `read`, `edit`, and `write` replace Pi's own. Pi's own `bash` stays:

```ts
import { createAgentSession, SessionManager } from "@earendil-works/pi-coding-agent";
import { createPiFsTools } from "@better-fs-tools/pi";
import { memoryStore } from "@better-fs-tools/read";

const cwd = "/work/repo";
const tools = createPiFsTools({ state: memoryStore(), applyPatch: true });

// read, edit, and write have the names of Pi's built-in tools, so they replace
// them. Pi's own bash stays.
const { session } = await createAgentSession({
  cwd,
  sessionManager: SessionManager.inMemory(cwd),
  customTools: [tools.read, tools.edit, tools.write, tools.applyPatch],
});

try {
  await session.prompt("Rename greet() to welcome() in src/greet.ts.");
} finally {
  session.dispose();
}
```

The active tools of this session are `read`, `bash`, `edit`, `write`, and `apply_patch`.

### Choose the active tools

Three options of `createAgentSession()` choose which tools the model gets:

| Option         | Effect                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------ |
| `tools`        | An allowlist of tool names. Only these tools are active. A custom tool must be in the list too               |
| `excludeTools` | A list of tool names to turn off. It applies after `tools`                                                   |
| `noTools`      | `"builtin"` turns off Pi's built-in tools and keeps custom and extension tools. `"all"` starts with no tools |

This session can read and search, but it cannot change files. `read` is the Better FS Tools `read`:

```ts
import { createAgentSession, SessionManager } from "@earendil-works/pi-coding-agent";
import { createPiFsTools } from "@better-fs-tools/pi";

const cwd = "/work/repo";
const tools = createPiFsTools();

// A read-only session: the Better FS Tools read, and Pi's grep, find, and ls.
const { session } = await createAgentSession({
  cwd,
  sessionManager: SessionManager.inMemory(cwd),
  customTools: [tools.read],
  tools: ["read", "grep", "find", "ls"],
});
session.dispose();
```

### Add hooks and guards with an inline extension

`customTools` only adds tools. To also use Pi events, for example a `tool_call` guard, or a bash `afterRun` hook that calls `invalidate()`, write an extension function. Give it to `DefaultResourceLoader` in `extensionFactories`. Pi loads it as it loads an extension file:

```ts
import {
  createAgentSession,
  DefaultResourceLoader,
  getAgentDir,
  isToolCallEventType,
  SessionManager,
} from "@earendil-works/pi-coding-agent";
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { createPiBashTool, createPiFsTools } from "@better-fs-tools/pi";
import { memoryStore } from "@better-fs-tools/read";

const cwd = "/work/repo";

function fsToolsExtension(pi: ExtensionAPI): void {
  const tools = createPiFsTools({ state: memoryStore() });
  const bash = createPiBashTool({
    afterRun: [
      {
        id: "invalidate-package-json",
        afterRun: async (_outcome, ctx) => {
          await tools.invalidate("package.json", ctx.call);
          return {};
        },
      },
    ],
  });
  pi.registerTool(tools.read);
  pi.registerTool(tools.edit);
  pi.registerTool(tools.write);
  pi.registerTool(bash);

  // A guard: Pi calls tool_call handlers before each tool runs.
  pi.on("tool_call", async (event) => {
    if (isToolCallEventType("bash", event) && /\bgit\s+push\b/u.test(event.input.command)) {
      return { block: true, reason: "git push is not allowed in this host" };
    }
    return undefined;
  });
}

const resourceLoader = new DefaultResourceLoader({
  cwd,
  agentDir: getAgentDir(),
  extensionFactories: [{ name: "better-fs-tools", factory: fsToolsExtension }],
});
await resourceLoader.reload();

const { session } = await createAgentSession({
  cwd,
  resourceLoader,
  sessionManager: SessionManager.inMemory(cwd),
  // Turn off Pi's built-in tools. The extension's tools stay active.
  noTools: "builtin",
});

try {
  await session.prompt("Update the version in package.json to 2.0.0.");
} finally {
  session.dispose();
}
```

With `noTools: "builtin"`, the active tools are the four tools of the extension. `DefaultResourceLoader` also finds the extension files in your user and project folders, as the `pi` command does. Set `noExtensions: true` to skip the extension files that Pi finds. The inline extensions still load.

### The working directory

The `cwd` of `createAgentSession()` is the `ctx.cwd` of each tool call. The tools use it as their only root. See [Each call uses ctx.cwd](#each-call-uses-ctxcwd). Give the same directory to `createAgentSession()`, to `DefaultResourceLoader`, and to `SessionManager.inMemory()`. One session works in one directory. For a second directory, make a second session.

`SessionManager.inMemory()` keeps the conversation in memory and writes no session file. A `memoryStore()` also keeps its read records in memory only, so each new process starts with no reads.

### One copy of Pi

`piMutationQueueLocks()` uses the file queue of the `@earendil-works/pi-coding-agent` module that the package imports. In an SDK host, install one copy of Pi, so that the package and your session use the same module. With two copies, a Better FS Tools `edit` and Pi's own `write` on the same file do not wait for each other. `npm ls @earendil-works/pi-coding-agent` shows the copies.

For a host on `pi-agent-core` without the coding agent, see [Pi agent core](/hosts/pi-agent-core). For the durable harness, see [Pi durable](/hosts/pi-durable).

## Each call uses ctx.cwd

Pi gives each tool call an `ExtensionContext`. The tools use its `cwd` as the only allowed root of that call. The tool reads and writes through `nodeFileSystem` with `cwd: ctx.cwd` and `allowedRoots: [ctx.cwd]`. When the working directory changes between calls, the root changes too.

You cannot widen the root. `fs`, `cwd`, and `allowedRoots` throw `TypeError` in every Pi factory:

```text
TypeError: Pi read tool options cannot set cwd: the root is bound to ctx.cwd on every call
```

A call without a `ctx.cwd` string throws `TypeError` too.

The tools keep the filesystems of the last 8 working directories. A ninth directory removes the oldest one from the cache.

The `ExtensionContext` is the host of the call. Your host functions get it as `ctx.call.host`. For example, an `askUser()` function can call `ctx.call.host.ui.confirm(...)`, and a `state` factory on `createPiReadTool()` can call `ctx.call.host.sessionManager.getSessionId()`. See [Hooks and state](/guides/read/hooks-and-state).

## Root options

These options set the filesystem of each call. In `createPiFsTools()`, set them once at the top level. `createPiReadTool()` takes only `denyRoots` and `symlinks`.

| Option             | Default                        | Meaning                                                                                                                                               |
| ------------------ | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `denyRoots`        | none                           | Paths that are refused as `DANGEROUS_PATH`, in addition to `/dev`, `/proc`, and `/sys`                                                                |
| `symlinks`         | `"follow-within-roots"`        | `"reject"` refuses every symlink. `"follow-within-roots"` follows a link when its real path stays inside `ctx.cwd`                                    |
| `hardLinks`        | `"in-place"`                   | How to write a file with more than one hard link. `"in-place"` writes through the link, which is not atomic. `"refuse"` fails the write with `DENIED` |
| `newFileMode`      | `0o666` less the process umask | The exact mode of a new file                                                                                                                          |
| `newDirectoryMode` | `0o777` less the process umask | The exact mode of a new directory                                                                                                                     |

```ts
import { createPiFsTools } from "@better-fs-tools/pi";

const tools = createPiFsTools({
  symlinks: "reject",
  hardLinks: "refuse",
  newFileMode: 0o644,
  newDirectoryMode: 0o755,
});
```

A file with one hard link is always replaced with a temporary file and a rename.

## Tool shapes

The default signatures follow Pi's own tools, so the model sees the input it knows, and Pi's renderers fit the results:

| Tool          | Default signature                        | Model input                                                     |
| ------------- | ---------------------------------------- | --------------------------------------------------------------- |
| `read`        | `defaultReadSignature({ name: "read" })` | `{ path, offset?, limit? }`, with integer `offset` and `limit`  |
| `edit`        | `multiEditSignature()`                   | `{ path, edits: [{ oldText, newText }] }`                       |
| `write`       | `defaultWriteSignature()`                | `{ path, content }`                                             |
| `apply_patch` | `freeformPatchSignature()`               | `{ patch }`, plus the Codex patch grammar                       |
| `bash`        | set by `createPiBashTool()`              | `{ command, timeout? }`, with `timeout` in seconds and no `cwd` |

The read schema has integer `offset` and `limit`. A model that sends `2.5` gets Pi's validation error.

`edit` takes one or more pairs in `edits`. Each `oldText` is matched against the original file, as Pi's own `edit` does. When you pass `matchers` to the edit tool, the default signature describes the same matchers to the model.

`apply_patch` sets Pi's `constrainedSampling` with the Codex patch grammar. A model that supports grammar tools gets the grammar. Other models get the JSON schema.

Set `signature` on a tool to change its name, its parameter names, or its descriptions. See [Customise the tool definition](/hosts/tool-definition).

## Prompt snippets and guidelines

Pi puts a short snippet and a list of guidelines for each tool in its system prompt. The defaults are the text of Pi's own tools, so the system prompt stays the same when you replace them:

| Tool          | `promptSnippet`                                                                                      | `promptGuidelines`                                                                                                |
| ------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `read`        | `Read file contents`                                                                                 | `Use read to examine files instead of cat or sed.`                                                                |
| `edit`        | `Make precise file edits with exact text replacement, including multiple disjoint edits in one call` | Four lines from Pi's own `edit`. The first is `Use edit for precise changes (edits[].oldText must match exactly)` |
| `write`       | `Create or overwrite files`                                                                          | `Use write only for new files or complete rewrites.`                                                              |
| `apply_patch` | `Add, update, move, or delete files with one patch`                                                  | `Use apply_patch for related changes across several files, or to add, move, or delete files.`                     |
| `bash`        | `Execute bash commands (ls, grep, find, etc.)`                                                       | none                                                                                                              |

Set `promptSnippet` or `promptGuidelines` on a tool to replace the default. A list you pass replaces the whole list:

```ts
import { createPiFsTools } from "@better-fs-tools/pi";

const tools = createPiFsTools({
  edit: {
    promptGuidelines: ["Use edit for precise changes. Copy each edits[].oldText from the file."],
  },
});
```

### The edit guideline says "exact match"

Pi's own guideline says that `oldText` must match exactly. The tool also accepts close matches. When the exact text is not found, the [normalized matcher](/guides/write/matching#loose-matches) can find text that differs by trailing spaces, Unicode forms, curly quotes, dashes, or special spaces. The result then has a note:

```text
Edited word.ts: 1 replacement at line 1.

[edit:fuzzy-match] Edit 1 matched word.ts at line 1 only with the normalized matcher, not exactly. Check the result.
```

The default guideline stays the same as Pi's own. Set `promptGuidelines` if you want the prompt to say that close matches work.

## Results in Pi

Each tool returns Pi `content` parts and Pi `details`. A tool error becomes Pi content text with `isError: true`. The tool does not throw for a tool error. Pi shows the text as an error, and a `tool_result` handler sees `isError: true`:

```text
[edit:not-read] Read greet.ts with the read tool before changing it.
```

An image part becomes a Pi `image` part. Other media becomes a text part that says what was left out, because Pi's tool content takes images only.

| Tool                  | `details`                                                                                                       |
| --------------------- | --------------------------------------------------------------------------------------------------------------- |
| `read`                | `{ truncation }` when the read stopped exactly at a line or byte limit, else `{}`                               |
| `edit`, `apply_patch` | `{ diff, patch, firstChangedLine }`, the shape of Pi's `EditToolDetails`. `undefined` for an error or no change |
| `write`               | `undefined`, as for Pi's own `write`                                                                            |
| `bash`                | `{ fullOutputPath }` when the output spilled to a file, else `undefined`                                        |

### Errors, output schemas, and hints

Each tool sets the Pi 1.x tool fields that Pi's own tools set, and some more:

| Tool                  | `isError`                                      | `outputSchema` and `structuredContent`                                                            | `annotations`                                                            |
| --------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `read`                | `true` for status `error`                      | Pi's own read schema: the text, or `{ type: "image", data, mimeType, note }`                      | `readOnlyHint: true`                                                     |
| `edit`, `apply_patch` | `true` for status `error`                      | None, as Pi's own `edit`. Codemode scripts get the text                                           | `destructiveHint: true`, `idempotentHint: false`, `openWorldHint: false` |
| `write`               | `true` for status `error`                      | None, as Pi's own `write`                                                                         | As `edit`, with `idempotentHint: true`                                   |
| `bash`                | `true` for a nonzero exit, a timeout, an error | Pi's own bash schema: `output`, `truncated`, `full_output_path`, `exit_code`, `wall_time_seconds` | None                                                                     |

A failed `read` has no `structuredContent`. A codemode script that calls it then gets a rejection, as with Pi's own `read`. A `bash` command that exits with a nonzero code keeps its `structuredContent`, so the script gets the exit code. A timeout or an abort has none. `structuredContent.output` is the output that the tool kept: the head and the tail, with Pi's `[... N bytes omitted ...]` marker between them.

A read with status `unsupported`, for example of a binary file, is not an error. Its text tells the model why the tool did not show the file.

Permission extensions read `annotations` from `pi.getAllTools()`. Pi does not check the hints.

### Read truncation

`details.truncation` has the shape of Pi's `TruncationResult`. Pi uses it to print how many lines it shows. Its `content` is the output of the formatter in `"view"` mode, without the notes. The details are `{}` for any other result: a read that did not stop at a line or byte limit, a total that is not exact, or a formatter that returns parts. An approximate count is worse than none. See the [read formatting guide](/guides/read/formatting) for the `"view"` mode.

### Edit diff

`details.diff` is the display diff that Pi's edit renderer draws. Context and removed lines carry the old line number. Added lines carry the new one. `details.patch` is the unified diff of every change. With more than one file, as from `apply_patch`, each file's lines follow a line with its path.

```text
 1 export function greet(name: string): string {
-2   return `Hello, ${name}!`;
+2   return `Hi, ${name}!`;
 3 }
```

### Details for your own tool

`toPiReadDetails()` and `toPiMutationDetails()` build the same details for a tool that you build yourself on the core:

```ts
import { toPiMutationDetails, toPiReadDetails } from "@better-fs-tools/pi";
import { nodeFileSystem } from "@better-fs-tools/node";
import { createReadTool, lineNumberFormatter, resolveReadLimits } from "@better-fs-tools/read";
import { createEditTool } from "@better-fs-tools/write";

const cwd = process.cwd();
const fs = nodeFileSystem({ cwd, allowedRoots: [cwd] });

const edit = createEditTool({ fs });
const changed = await edit({
  path: "src/greet.ts",
  edits: [{ oldText: "Hello", newText: "Hi" }],
});
const editDetails = toPiMutationDetails(changed);

const limits = resolveReadLimits({ maxLines: 2 });
const formatter = lineNumberFormatter();
const read = createReadTool({ fs, limits, formatter });
const call = { callId: "call-1", host: undefined };
const result = await read({ path: "src/greet.ts" }, call);
let view: string | null = null;
if (result.status === "ok") {
  const { content: _content, ...outcome } = result;
  const text = formatter.format(outcome, { digest: null, limits, mode: "view", call });
  view = typeof text === "string" ? text : null;
}
const readDetails = toPiReadDetails(result, view, limits.maxViewBytes);
```

`toPiReadDetails(result, view, maxViewBytes)` takes the read result, the formatted text in `"view"` mode or `null`, and the view byte limit. `toPiMutationDetails(result)` takes the result of `edit` or `apply_patch`.

## Bash tool

`createPiBashTool()` is a `bash` tool from `@better-fs-tools/shell` in Pi's own shape. It takes `{ command, timeout }`, with the timeout in seconds, and has Pi's prompt snippet. The extension entry does not register it. Pi's own `bash` stays unless you register this one:

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { createPiBashTool } from "@better-fs-tools/pi";

// Replaces Pi's own bash: same name, { command, timeout } in seconds, run in ctx.cwd.
export default function bashExtension(pi: ExtensionAPI): void {
  pi.registerTool(createPiBashTool());
}
```

The command runs in `ctx.cwd` on every call. This is also true with a `runner` that you pass: the runner gets `ctx.cwd` as the `cwd` of the request, not its own `cwd`. A relative `ctx.cwd` throws:

```text
TypeError: Pi bash execution requires an absolute ctx.cwd
```

The options take every `createBashTool()` option except `cwd`, plus `runner`, `signature`, `promptSnippet`, and `promptGuidelines`. `fs`, `cwd`, and `allowedRoots` throw `TypeError`, as in the file tools.

| Option      | Default                                                        |
| ----------- | -------------------------------------------------------------- |
| `runner`    | A `nodeCommandRunner` at `ctx.cwd`, one for each directory     |
| `env`       | `shellEnv(() => process.env)`                                  |
| `signature` | Pi's `{ command, timeout }` input, with the timeout in seconds |

The default description names the timeouts and output limits from `limits`, and the id of a `runner` object when you pass one. See the [bash guide](/guides/bash) for limits, policy, and runners.

Pi's own `bash` also sets `PI_*` session variables. This tool does not. Add them with the `env` option when you need them.

When the output is too long, the tool can save it to a file. `details.fullOutputPath` gives that file to Pi's bash renderer. See [Limits](/guides/bash/limits).

## Forget a read after a bash command

A bash command can change a file after the model read it. With a read store, call `invalidate()` from a bash `afterRun` hook. The next edit of that file then needs a read:

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { createPiBashTool, createPiFsTools } from "@better-fs-tools/pi";
import { memoryStore } from "@better-fs-tools/read";

// The file tools with a read store, and Pi-shaped bash. After each command,
// the next edit of package.json needs a read, since the command may have
// changed it.
export default function fsAndBashExtension(pi: ExtensionAPI): void {
  const tools = createPiFsTools({ state: memoryStore() });
  const bash = createPiBashTool({
    afterRun: [
      {
        id: "invalidate-package-json",
        afterRun: async (_outcome, ctx) => {
          // ctx.call carries Pi's ctx, so the path resolves under its cwd.
          await tools.invalidate("package.json", ctx.call);
          return {};
        },
      },
    ],
  });
  pi.registerTool(tools.read);
  pi.registerTool(tools.edit);
  pi.registerTool(tools.write);
  pi.registerTool(bash);
}
```

Pass the call to `invalidate(path, call)`. In a bash `afterRun` hook, the call is `ctx.call`. The path resolves under the `ctx.cwd` of that call. In the other bundles the call is optional, but the Pi bundle has no root until a call gives one. Without the call, `invalidate()` does not throw. It returns `{ ok: false }` with reason `unsupported`:

```json
{
  "ok": false,
  "phase": "stat",
  "error": {
    "reason": "unsupported",
    "detail": "fs is a factory: pass the call context to invalidate(path, call)"
  }
}
```

With the call, the outcome is `{ ok: true, resolvedPath, recorded }`. `recorded` is `true` when the store had a record for the path. With `state: null`, `recorded` is `false`.

## Locks

`piMutationQueueLocks()` is a lock manager over `withFileMutationQueue()`, the per-file queue of Pi's own `edit` and `write`. It is the default of `createPiFsTools()` and of each single write factory. A Better FS Tools `edit` and Pi's own `edit` or `write` that change the same file then wait for each other.

| Option      | Default  | Meaning                                                                                 |
| ----------- | -------- | --------------------------------------------------------------------------------------- |
| `timeoutMs` | `30_000` | How long a change waits for its files. After that, the change fails with `LOCK_TIMEOUT` |

In a Pi extension, Pi's loader gives the package Pi's own module, so the queue is Pi's. In an SDK host, see [One copy of Pi](#one-copy-of-pi). To use a lock manager of this process only, as in 0.2.0, pass `locks: memoryLocks()` from `@better-fs-tools/write`:

```ts
import { createPiFsTools, piMutationQueueLocks } from "@better-fs-tools/pi";
import { memoryLocks } from "@better-fs-tools/write";

// Wait 5 seconds for Pi's queue, then fail the change with LOCK_TIMEOUT.
export const tools = createPiFsTools({ locks: piMutationQueueLocks({ timeoutMs: 5_000 }) });

// Or do not wait for Pi's own tools.
export const separate = createPiFsTools({ locks: memoryLocks() });
```

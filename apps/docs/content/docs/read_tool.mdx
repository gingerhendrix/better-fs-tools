## What's in a Read Tool?

The read tool has a simple job, read from the filesystem and return the contents of a file. However, there is a surprising amount of variation in how this is implemented across different harnesses.

### Signature

Do you even need a read tool? Codex says no, just use the shell, but it stands alone in the harnesses surveyed and though it's an attractive idea to me, it would make dfor a crap article. How about two read tools? Back in the day, a read multiple files tool was common, but that has fallen out of favour since parallel tool calls are now widespread, Gemini CLI and (FACT CHECK) are the only harnesses that sill ship one.

Other than that, there is general consensus of the shape - a single tool that takes the path to a file along with optional offset and limit parameters. The name of the tool is usually `read`, `Read` (Claude) or `read_file`, with either a `path`, `filePath` or `file_path` first argument and there is strong agreement on `limit` and `offset` as the remaining parameters. FACT CHECK is the odd one out with `start_line` and `end_line` replacing `offset` and `limit`.

Command Code retains read multi-file read capabilities with an optional `paths` (array of absolute paths or glob patterns) and additional `target_directory`, `exclude` (FACT CHECK)

#### Docs

The tool signature passed to the LLM is accompanied by a description that serves as documentation for the LLM on how to use the tool. Cloudflare Computer currently holds the prize for minimalism:

<blockquote style={{ quotes: "none" }}>
  Read a workspace file. Images and PDFs are passed to capable models. Text output is capped at 2000
  lines or 256KB and includes line and byte continuations when truncated.
</blockquote>

OpenCode has one of the most verbose (though oh-my-pi is the supreme champion here with over 3000 chars of tool description, but that is mostly due to OMP's virtual filesystem)

<blockquote style={{quotes: 'none'}}>
Read a file or directory from the local filesystem. If the path does not exist, an error is returned.

Usage:

- The filePath parameter should be an absolute path.
- By default, this tool returns up to 2000 lines from the start of the file.
- The offset parameter is the line number to start from (1-indexed).
- To read later sections, call this tool again with a larger offset.
- Use the grep tool to find specific content in large files or files with long lines.
- If you are unsure of the correct file path, use the glob tool to look up filenames by glob pattern.
- Contents are returned with each line prefixed by its line number as `<line>: <content>`. For example, if a file has contents "foo\n", you will receive "1: foo\n". For directories, entries are returned one per line (without line numbers) with a trailing `/` for subdirectories.
- Any line longer than 2000 characters is truncated.
- Call this tool in parallel when you know there are multiple files you want to read.
- Avoid tiny repeated slices (30 line chunks). If you need more context, read a larger window.
- This tool can read image files and PDFs and return them as file attachments.

</blockquote>

### Output

From the LLM's perspective, the next thing that matters is how the output is formatted. Broadly this comes down to delimiters, line numbering and additional info for truncation and additional messages to accompany the output.

OpenCode wraps its output with tags and numbers the lines (with colon-space as the delimiter).

```
<path>/repo/src/app.ts</path>
<type>file</type>
<content>
1: import { x } from "./x"
2: export const y = x

(End of file - total 2 lines)
</content>
```

DeepAgents has recently switched to a new new format instead of their previous line numbered output which the claim reduces edit errors by 15% and token usage by 10%. The new format simply delimits the content

```
@@ lines 1-100 of 250 | next offset 100 @@
import { x } from "./x"
export const y = x
@@ lines 1-100 of 250 | next offset 100 @@
```

### Implementation

Implementation details dont matter as much to the LLM, but there are still a number of ways they affect the agent experience.

(return to headings, add small summary tables where possible)

- **Path Handling**: Path handling is a rabbit hole of edge cases, my favourite edge case I discovered when researching this is that macOS uses a narrow no-break space (U+202F) in the filename for screenshots (Claude, Pi and others account for this, but its not universal). Most harnesses support some kind of path repair, either silently fixing the path, fixing it with a note to the LLM, or returning a not found error with suggestions.
- **Permissions**: Most harnesses have some form of permission handling that must run after the path is resolved, either to deny certain directories or to prompt the user for permission. Hermes has the most interesting set of forbidden directories, including variations of `.env` and `/proc/*/environ` to try to prevent accidental disclosure of secrets.
- **Binary detection**: Dumping binary files to the LLM is an expensive mistake so all the harnesses attempt binary detection. The robustness of this varies with Deep Agents and Mastra relying on just a file extension check, while others use some form of byte sampling.
- **Images**: Since most models can handle image input natively, most harnesses will return the image to the LLM. (Fact check: most dont process the image but ...)
- **File Conversion**: For other formats, some harnesses will attempt to convert the file to text, either by using a library or by calling an external tool. Claude supports PDF, Hermes, Command Code, and oh-my-pi have a variety of formats they can convert - (fact check: list formats).
- **Limits**: Limits are weirdly consistent at 2000 lines of content (fact check count of survey), it's key here to also account for a line length limit and a total byte limit which most harnesses do well. The LLM also needs to know that the output has been truncated and fairly similar messages are used across the harnesses.
